# Read lists over Jira's REST search

Lazyjira reads ticket and epic lists, and prefetches ticket details, with Jira's REST search through the `jira_rest` client, not one `jira` CLI process per query. A list refresh costs one paginated search (a page holds 500 tickets) however large the team roster grows, where the CLI cost two processes per member (a Go startup and a round-trip each). Epics cost one search per 50 epics for their children and one per 50 children for their sub-tasks, so about 50 searches for 400 epics with about 2000 children, run four at a time (the limit is per read, so an epics refresh and a detail prefetch can have eight out at once), where the CLI cost one process per epic page and two per epic. The search also returns what jira-cli's plain list output can't: each assignee's email, labels, the parent of a sub-task and the update time. Team groups by Jira's own assignee email instead of the email each query was made with, labels show on first paint instead of after a detail fetch, and sub-task parents arrive in the same read. Reads use the same jira-cli config (`server`, `auth_type`, `login`, and the Epic Link field `epic.link`) and `JIRA_API_TOKEN` that moves use, so lists now need the token as well: without it a refresh fails with a message and the last snapshot stays on screen. There is no CLI fallback for list reads; keeping two read paths would double the formats to maintain, and the demo recording is served by a small fake Jira REST endpoint instead.

The search is `POST /rest/api/2/search`, paged with `startAt` and `total`, which Jira Server and Data Center serve. It was built and measured against a Data Center instance (`installation: Local` in jira-cli's config). Jira Cloud's newer search paginates by token without a total, so Cloud isn't supported; an answer with no `total` is an error rather than a short list.

JQL that jira-cli used to scope silently (`project = "KEY"`) is now added by lazyjira. This supersedes the read half of [ADR 0001](0001-use-jira-cli-and-rest-transitions.md): creation, comments, assignment and field edits still go through jira-cli, along with `jira me`. A single ticket's fresh detail (opening it, or the refetch after a move) is read with `GET /issue/{key}`, not a search, because the search reads Jira's index, which can lag a move made a moment ago; the same parser reads both. Missing details are prefetched through the search, 50 tickets to a request. Neither asks for the changelog, which `jira issue view --raw` didn't return either, so activity is comments. It also folds [ADR 0004](0004-read-subtask-parents-over-rest.md)'s separate sub-task search into the list search for lists; a parent is still never taken from the details cache.

Team groups by exact email, so emails are normalized (lower case) where they enter the app. A ticket is placed on the roster by email, else by the assignee's display name, because Jira can hide an assignee's email; an assignee that can't be placed joins Team instead of the ticket being dropped. "Jira search" here is this REST call, not the local text filter that CONTEXT.md calls Search.

**Update:** epics no longer cost a search per 50 epics and per 50 children. Measured on that instance (416 epics, 2,278 children with their sub-tasks), `"Epic Link" in (50 keys)` took about a second a search, and the 44 searches of a refresh 7.5 to 9 seconds. A refresh now sends three reads at once: the epic list, every ticket in the project with an Epic Link, and every sub-task in the project, placing what belongs to an epic and leaving out the rest. Jira Server rejects `parent is not EMPTY`, so children that name their epic through `parent` are still searched 50 epics at a time. A search's pages after the first are asked for four at a time. The same refresh takes 1.7 to 2.4 seconds on warm connections (16 requests), where it took 7.5.
