# lazyjira architecture

The rules behind lazyjira's reads, caches, statuses, moves and rows: what the code must keep true, and why. User-visible behaviour and keybindings are in [README.md](../README.md); the decisions with their alternatives are in [docs/adr/](adr/).

## Key Design Decisions

### Epics come from project-wide searches
The Epics tab's `jira_reads::fetch_epics` reads through `jira_rest::search` too, not one `jira` process per epic. `read_epics` sends three reads at once: the epic list (`epics_jql`), every ticket in the project with an Epic Link (`children_by_epic_link_jql`) and every sub-task in the project (`subtasks_jql`). The last two ask for more than the epics hold (children of other projects' epics, sub-tasks of tickets in no epic) because asking by key was slow: on the Data Center instance this was measured on, `"Epic Link" in (50 keys)` cost about a second a search, nine of them for 416 epics, and the sub-tasks then needed the children's keys, 34 more searches. A project-wide search waits for nobody's keys and costs a few pages (see "Lists come from one Jira search" for how pages are read).

A child names its epic through the Epic Link field (company-managed projects) or `parent` (team-managed). The Epic Link search is left out when jira-cli's config has no `epic.link`, since the field would then be unreadable and the JQL could fail, so only `parent` links are found there. Jira Server rejects `parent is not EMPTY`, so `parent` children are still asked for by key once the epic list is in: `children_by_parent_jqls` builds one search per `jql::KEYS_PER_SEARCH` (50) epic keys, and `jira_search::search_in_order` runs `SEARCHES_AT_ONCE` (4) at a time (`bounded::try_in_order`) and returns their tickets in query order, stopping the queued ones from being sent once one fails. `lists::group_by_epic` puts each child under the epic its `epic_key` names (the Epic Link value, else a non-sub-task's `parent`), once each and sorted by key; a child of an epic that isn't listed is dropped. `subtasks::add_to_epics` adds the sub-tasks of the children, which Jira doesn't link to the epic, so progress counts them; a sub-task whose parent is in no epic is left out. Any failed search, sub-tasks included, fails the refresh (`refresh_epics_cache` returns the error), so the epics already on screen and in the cache stay instead of being replaced by epics with a different progress.

The limits aren't shared, so they add up: every search reads its own pages `PAGES_AT_ONCE` at a time, and an epics refresh runs its `parent` searches, `SEARCHES_AT_ONCE` at a time, beside the two project-wide searches, and the list search and a detail prefetch can run beside that: startup and a manual refresh (`r`, after creating tickets, after a settings change) send the epics and the lists at once, so the epics never wait for the lists, and a manual refresh supersedes an epics read already out, aborting it (`App::epics_read`) so its older epics don't reach the epics cache file (unless it was already saving when aborted, no worse than one that finished just before). Either can land first, so a list read carries no epics: `App::show_refreshed_lists` keeps the epics on screen and puts the new tickets in them (`attach_epics_to_tickets`, `reconcile_epic_child_statuses`). The epics cache is read once, at startup, over the snapshot's epics: every epics read that succeeds and isn't superseded writes it, while the snapshot is written only when lists land. `replace_epics` fills the epic children's details from `App::details`. On the project measured (4 pages of Epic Link children, 2 of sub-tasks, one page per `parent` search) an epics refresh has at most 8 requests out at once.

### Lists come from one Jira search
My Work, Team and Unassigned come from one paginated `jira_rest::search` ([ADR 0005](adr/0005-read-lists-over-jira-rest-search.md)), not per-member CLI queries. A search's first page says how many tickets match and how long a page is (500, or the server's cap); `jira_rest::read_pages` then asks for the rest by that length, each once, `PAGES_AT_ONCE` (4) at a time, and reads them in page order. An empty page ends the search; a page shorter than the first with matches still after it sends the search back to one page after another from where it ended (`read_pages_from`), so no ticket is skipped. `jql::lists_jql` builds it from the config: the roster's active tickets (plus those done inside the window for the full scope) and the active tickets nobody has taken that are the team's by Assigned Teams. A REST search needs the project and an order spelled out, so every builder adds them (`scoped_jql` for saved filters, keeping their own ORDER BY), and every config string in a query goes through `jql::quote`.

Emails are normalized (`cache::normalize_email`) where they enter the app (Jira's issues, the roster, `jira me`), so everything after compares them exactly. `lists::bucket_tickets` splits the results: a ticket is placed on the roster by email, else by the assignee's display name, since Jira can hide emails; an assignee it can't place joins Team under their email (or display name) rather than dropping the ticket; no assignee becomes the Unassigned member's; My Work is the tickets of the current user's email. The Epic Link field id is jira-cli's `epic.link` (`jira_rest::epic_link_field`), never a hard-coded `customfield_` id. A search answer without a `total` is an error, not a short list. A failed search (including a missing `JIRA_API_TOKEN`) propagates out of `fetch_with_scope`, so `replace_cache` isn't called and the last snapshot stays; with no snapshot, startup restores the terminal and exits with the error.

### Detail data uses JSON + local cache
Rich ticket detail (description, reporter, comments as activity) is cached locally, and is hydrated on startup for fast detail open. Hydration (`hydrate_ticket_from_details_cache`) fills only those detail-only fields and the stored `detail_loaded`: labels, assignee, epic and parent come from the list search and the cache must not bring back stale values.

The details cache file is read once at startup into `local_cache::DetailCache` (`App::details`); `fetch_active_only` and `fetch_all` hydrate from that in-memory copy before returning, so no caller can forget to, and a background task writes it back once details stop arriving for 750 ms. `DetailCache::close` (called when the app quits) writes the file itself rather than asking that task, so details recorded in the last moments aren't lost and a stalled task can't hold up quitting. It also drops the details of tickets no loaded list holds any more (`App::listed_keys`: My Work, Team, every epic's children and the filter results), so the file doesn't grow with every ticket ever seen; with nothing listed (the lists never loaded) it drops nothing, and a dropped ticket is simply refetched when opened.

`App::replace_epics` hydrates the epic children it is given from the same copy.

Missing details are prefetched in the background by `jira_search::fetch_ticket_details`: one `jira_rest::search` (`key in (...)`, asking for the list fields plus `DETAIL_ONLY_FIELDS`) per `KEYS_PER_SEARCH` (50) tickets, `SEARCHES_AT_ONCE` (4) chunks at a time, and each ticket's result goes to the app in its own `TicketDetailFetched`, so `enrich_ticket` and the move guard see each as a single-ticket detail. A chunk that fails (or a ticket Jira leaves out) fails only those keys: they stay missing and are asked for again on the next refresh, and the other chunks are still read.

A cached detail is never refreshed on its own (it is only pruned at quit), so opening a ticket's detail always fetches Jira's copy too (`App::open_fresh_detail`, through `jira_rest::issue`, as does the refetch after a move): the cached detail shows at once and is replaced when the fetch lands. That read is `GET /issue/{key}`, not a search, because the search reads Jira's index, which can lag a move made a moment ago. Neither read asks for the changelog, so activity is comments.

### Local caches
The snapshot, epics, ticket details and the current user's email (from `jira me`, refreshed in the background at startup once one is remembered) live in `~/.cache/lazyjira/`, per project, readable by the user only (directory 0700, files 0600: they hold descriptions and comments). Each is written through a temp file renamed over the cache file (`write_cache_text`), so overlapping saves (quit and the details writer, two lazyjira instances) and a crash never leave a half-written one; a cache directory or file an earlier build made readable by others is tightened when written. The epics and details caches 0.9.0 left in the system temp dir are ignored, and `local_cache::remove_old_temp_dir_caches` deletes this project's two files once at startup.

A cache that fails to parse is ignored and refetched, which is how format changes are handled: tickets store their status as `status_name`, so caches from before real status names are refetched once.

Tests use `lazyjira-test-<user>` in the temp dir instead (`local_cache::cache_dir`), with the process id in every file name so parallel runs don't share files; each test removes its files, and the directories it makes, even when it fails.

### Statuses
`Ticket::status` is Jira's own status name ("Resolved", "On Deck"), or `cache::UNKNOWN_STATUS` when a read's answer has none (so it shows plainly instead of passing as To Do; `enrich_ticket` never copies it over a real status). Views group, label and compare by it. `cache::StatusRules`, built from the `[statuses]` config, decides everything else about a status: the one display order (`active` in config order, then unlisted statuses in first-seen order, then `done`, then `dropped`) and whether it's done (`is_done`: `d` hides it, epic progress counts it unless it's dropped, Team puts it in the done split and leaves it out of active counts) and, through `kind` (`StatusKind`: Active, Done or Dropped), whether it's dropped: done work nobody did, from `dropped`, after every done status in display order. `Epic::progress` leaves dropped children out of both sides, `status_color` draws them gray (not dark gray, which the selected row's background already is), and a move to a dropped status isn't shipped, so no confetti or receipt line. A name in several lists takes the last of active, done and dropped. `dropped` never reaches JQL, which would fail on a status name the project lacks, so its defaults are safe; dropped tickets show where a read already finds them, such as epic children. Get it from `app.status_rules()`; don't sort statuses or test for done anywhere else. Names match case-insensitively. A name the config doesn't list takes the place of a listed name that `Status::from_str` reads the same way (so "Resolved" follows "Done"); failing that, Closed-like names are done and anything else is active.

The `Status` enum is only Jira-independent knowledge: move shortcut keys, default colors (`style::status_color`), and that fallback. `Status::from_str` reads Done/Closed/Resolved as `Status::Closed` and unknown names as `Status::Other`.

The `[statuses]` config also controls which statuses the JQL queries load.

### Moves use Jira's transitions
Each issue type has its own workflow, and a transition's name can differ from the status it leads to, so moves always send a transition id, never a status name. The picker lists the ticket's transitions from `GET /rest/api/2/issue/{key}/transitions?expand=transitions.fields` and sends the chosen one by id (`jira_rest`). Shortcuts match a transition's destination through `Status::from_str`. Transitions that differ only by id are merged when parsed. A resolution is asked for only when the transition has a resolution field, from that field's allowed values.

### Moves wait for Jira
A single-ticket move changes the ticket only after Jira reports success (`BackgroundMessage::TicketMoved`); a failure keeps the status and shows the error until dismissed. Every Jira read (detail fetch, cache/epics refresh, filter query) carries `requested_at = app.moves.now()`. That protects moves only; a read whose answer must not replace a newer read's also carries a request id (`App::next_request_id`, kept in `cache_refresh_request`, `epic_refresh_request` or `filter_request`), and an answer whose id is no longer the kept one changes nothing when it is applied. Reads requested before a ticket's latest confirmed move leave its status alone, so write statuses only through `App::enrich_ticket(key, requested_at, detail)`, `App::replace_cache(cache, requested_at)` or `App::reapply_moves_since`; never write them directly.

### Visible rows
App's grouped view methods return `VisibleGroup` values with header metadata, totals, and occurrence indices. Collapsed groups retain their header and totals but have no ticket rows. Navigation and renderers use these same groups; renderers compare supplied indices with `selected_index`. Keep tab-specific formatting in `views/`. Team members are ordered by active ticket count (most active first), with active tickets before done tickets.

Every grouped view method passes its tickets through `App::kept_by_search`, the one place that holds the search rule: a group whose header matches keeps all its tickets, any other group keeps the tickets that match, and a group left with none is dropped. A tab grouped by status passes its tickets as one group with no header. A new tab does the same; `every_tab_keeps_only_the_tickets_the_search_matches` runs over `Tab::all()` and fails for a tab that doesn't. The tabs differ in two ways around it. Team asks the search before it hides done tickets, so a member whose only matches are hidden stays with no rows, while Epics hides first and drops such an epic. And a search leaves out a member with no tickets even when it names them, while an epic it names stays with no children.

Each tab's folded group ids live in one private collection, `App::collapsed_groups`, indexed by `Tab::index`. Read it with `is_collapsed`; change it with `toggle_group_collapse`, `toggle_all_groups_collapse` (`Z`: it folds the groups the tab shows except the cursor's, so one hidden by a search, a status focus or epic pinning is left alone; a folded group makes it unfold them all, hidden or not), `show_filter_results` and `clear_filter_results`. `replace_cache` folds My Work's new done groups there too (`fold_new_done_groups`).

Use `App::switch_tab` to restore each tab's position, search, and status focus. Cache updates preserve the selected ticket occurrence and group through `mark_cache_changed`; use `replace_cache`, `replace_epics`, and the ticket update helpers so the old visible rows are retained before data changes.

Each item takes a range of lines: a group header one, a ticket one per summary line (see "Current UX behavior"). Renderers build a list's lines with `views::common::ListLines`: `status_header`, `group_header` and `ticket_row` add items, `note` and `push` add any other line, and `render` highlights the selected item's whole range, scrolls to keep its last line on screen (its first when it is taller than the list), registers mouse targets for the rows actually drawn and draws the list with no frame, padded by a three-cell gutter (a margin, the `›` marker or a group's dot, a space). A `mouse::Item` holds each item's range for `mouse::register_rows`: every drawn line of it selects the item, and only its first holds the gutter's mark (always a Mark target: three cells, five while tickets are marked, where a click marks) and the fold arrow; a group header's dot folds it. The top bar (`top_bar.rs`, two rows: the line and its rule) registers a target per tab and the Settings button. `ui` clears targets and selectable areas (`mouse::begin_layer`) before each layer that covers what is under it, so covered controls cannot receive clicks. The layers, bottom to top: the top bar, then the list (and the detail beside it, which clears the top bar's targets, see "Overlays"), then Help and Settings sheets, then the docked panel. Mouse actions share keyboard handlers and preserve confirmation steps. Text fields use the existing `tui-textarea` dependency and `widgets::form` helpers.

### Sub-tasks nest under their parent
`Ticket::parent_key` names a sub-task's parent. It comes from Jira's REST search on every list read: from the list search itself for My Work, Team, Unassigned and filters (`fetch_with_scope`, `fetch_jql_query`) and for epics' children, and from the project's sub-task search (`jql::subtasks_jql`, through the same `search`; [ADR 0004](adr/0004-read-subtask-parents-over-rest.md)) for the sub-tasks `fetch_epics` adds. Only those reads and a freshly fetched detail (through `enrich_ticket`) set it: `hydrate_ticket_from_details_cache` skips it so a re-parented ticket doesn't keep its old parent. A failed search fails the read, so rows stay as they were.

Sub-tasks of an epic's children count in epic progress (see "Epics come from project-wide searches"). Each tab passes its rows through `subtasks::nest` when building `VisibleGroup`s; Team nests its active and done rows separately, so a sub-task never moves between them. Renderers get a row's key and summary from `views::common::ticket_cells`: a sub-task whose parent is in the same rows is indented, and one whose parent isn't (a different status group, another assignee) leads its summary with the parent's key. `jira_issue::ticket_from_issue` reads a sub-task's `parent` as `parent_key`, never as an epic.

Folding a parent adds its key to `App::collapsed_parents` (one set for every tab). `nest` tags each row with its `Family` (a parent with a sub-task count, or a child); `index_groups` drops the children of folded parents from the rows but keeps them in `total` and `VisibleGroup::folded_subtasks`, and `VisibleGroup::family` carries the tags to renderers and to `selected_fold_parent`. So row counts that must include hidden rows (Team's header counts) come from `total`, never from `tickets.len()`, and Team splits active from done by status, not position. `z` goes through `App::toggle_fold_at_cursor`: the selected parent or sub-task folds its parent, anything else folds its group.

### The event loop sleeps until woken
`main`'s loop applies the background messages that have arrived (`wake::arrived`), draws when something changed, then waits in `wake::next` for one of three things: terminal input (crossterm's `EventStream`), a background task's `BackgroundMessage`, or, only while confetti falls, the next frame (`wake::FRAME`, 33 ms). Nothing polls, so a Jira answer is applied and drawn when it arrives and an idle app doesn't wake. What a message does to `App` lives in `background::apply`, which spawns nothing and reads nothing: it returns a `FollowUp` (prefetch details, save the snapshot, start the next refresh, with an epics read beside a manual one, fetch one ticket's detail) and the loop starts that work. So a new message gets its arm, and its test, there. Anything new that must change the screen without a key press needs a wake of its own: send a `BackgroundMessage`, or add a branch to `wake::next`. Between waits that ended without input (a background message, a frame), the stream keeps a thread waiting on the terminal, so whatever needs the terminal to itself must follow an input wake: `$EDITOR` (`edit_externally`) is only ever asked for by a key or click, and first-run setup reads the terminal itself before the stream exists.

### Themes recolor the finished frame
Renderers draw with plain ANSI colors, each used for one job: `DarkGray` is muted text as a foreground and the selected row as a background, `Gray` behind `Black` text is a button (`form::buttons`), `Cyan` is keys and focus, `Yellow` is the In Progress dot, pending and loading text (`style::warning`) and the chosen option, `Red` is errors (`style::error`), and so on; the active tab and a focused pane's title are `Cyan` (`Theme::role` lists them). `ui` ends with `Theme::apply`, which swaps those colors in the buffer for the theme's roles, like a terminal color scheme. So keep drawing with the ANSI color for the job, not a theme field, and code that finds things by color (the footer's key hints, the editor cursor) keeps working. Unset roles, and every role of `default`, leave the terminal's color. While settings are open, `ui` applies the highlighted theme instead of `App::theme`, which is how the picker previews.

## Current UX behavior
- Team view includes the current user (if not in the `[team]` config, inferred from `jira me` email).
- My Work and Team include Epic and Labels columns. An epic or labels every drawn row shares show once, muted, on a muted line at the top of the list instead (`views::common::Shared`, used by My Work, Team, Unassigned and Filters, each passing the `Columns` it has: only My Work and Team have Epic and Labels columns, and Unassigned, grouped by epic, leaves the epic off the line; Team draws it once, at the top of the list above its first member): rows with no epic don't count, the Epic column returns when two rows' epics differ, Labels keeps only the labels some rows lack, and a hidden column's width goes to the summary. The sub-tasks of folded parents count; rows of folded groups don't. A column is drawn at its full width or not at all: `Shared::trailing_widths` takes the room Summary and the two columns share and drops Labels, then Epic, until Summary keeps `SUMMARY_MIN` (37) columns, and Summary takes what is left, so My Work and Team show key, summary (and Team's status) and age at 80 columns. With the demo's 12 wide keys that is Epic from 86 columns and Labels from 110 on My Work (Team, with a 14 wide status: Epic from 100 and Labels from 120), two columns more while tickets are marked. The width is a threshold, not a squeeze, so the old floors for Epic and Labels are gone.
- Status columns (Team, Unassigned, Filters, Epics) are as wide as the longest status drawn (`views::common::status_width`), so a long one like "Waiting for Approval" doesn't push its row's summary out of line. Epics also lists each child's Assignee (`-` when nobody has it), as wide as the longest drawn name up to 24 columns. Only drawn rows count, as for `Shared`: folding a group or searching can narrow the columns. Summary takes what the other columns leave; when that is under its minimum (Team 14, Filters 12, Unassigned and Epics 18), `views::common::narrow_for_summary` narrows the other columns in order, each to its floor: Team's Status (8, once Epic and Labels are dropped); Epics' Assignee, then Status (8 each); Unassigned's and Filters' Status (8). Widths count display columns (`unicode-width`): `views::common::truncate` cuts by them, and `fit` cuts and pads every cell to them. A summary too long for its column ends "...", unless `preferences.wrap_summaries` (`App::wrap_summaries`) is on: then `views::common::ticket_cells` word-wraps it, by display columns, onto further lines under the summary, with the other columns blank there. Group headers, Epics' epic headers included, stay one line.
- An epic's progress bar (Epics headers and epic detail, `views::common::epic_bar`, `EPIC_BAR_WIDTH` cells) has no brackets and a run per status, done statuses first, then active, then dropped, each in display order (`Epic::status_counts`, which the epic detail's Status line follows too), each as wide as its share of the children, `DONE_CELL` (`█`) when done, `░` when dropped and `▒` when active, in `status_color`; an epic with no children draws `·`. `share_cells` gives the leftover cells to the largest remainders and a status that rounds to nothing one cell from the widest run, so a few Won't Do or Blocked tickets stay visible. Epics headers follow the bar with `Epic::percent_done` (the share of the children not dropped that are done, rounded down so only a finished epic shows 100%, and none when nothing is in scope) and each status's count in the same order ("97% done · 121 tickets: 108 Done · 3 In Progress · 10 Won't Do"). The epic detail shows the same percentage as "108 / 111 (97%)", followed by ", 10 dropped" so the numbers add up to the epic's children.
- `Enter` works while search is active (opens detail for selected row).
- Done status groups start folded. In My Work, `replace_cache` folds each done status the first time a read brings it, until the first full-scope read (Full or Manual) is applied through `App::replace_cache_full_scope`, which folds its own new done statuses and then ends folding, since the snapshot and the active-only read may lack done tickets. A failed read changes nothing. After that no read folds, so an unfolded group stays open and a group that first appears mid-session (a ticket just closed) shows open. In Filters on every query (`App::show_filter_results`).
- No emoji, and no glyph that isn't one column by `unicode-width`, is drawn: `every_cell_on_every_tab_and_overlay_is_one_column_wide_at_80_120_and_160_columns` fails when one comes back, so columns and overlays never misalign. A new glyph is checked with `UnicodeWidthStr::width(..) == 1`.
- The idle footer (`footer.rs`) is a list of `Hint`s (key, label, priority) and one muted segment at the right. `footer::fit` drops the segment first when it doesn't fit beside every hint, then hints from the highest priority number and, within one, from the right, so a hint is whole or gone; `? more` has priority 0 and stays. The segment names only what differs from the defaults (hidden Done, a focused status, syncing or refreshing, stale age, epics syncing; on Filters only the results pane, when it has focus). Filters has its own hint set. While tickets are marked, the bulk bar above the footer (`footer::bulk_bar`) shows `N selected   B move or assign · u clear · A all`, and the footer's segment leaves the count out. In spooky season `S settings` leads until the spooky theme is chosen. Every footer key must be in the help (`every_footer_key_is_in_the_help`). Flash, search and pending-move messages still replace the footer. Styles come from `style.rs`, one function per role in `docs/tui-style.md`, in the ANSI colors `theme.rs` recolors.
- Marking is a mode: the checkbox (☐ unselected, muted, ☒ selected, ⊟ some of a group, one column each, from `views::common`: `ticket_marker`, `group_marker`) is drawn only while `App::is_marking()`, after the gutter and before the key, and every row and header gets one. `ListLines::lead` builds the gutter (`gutter`: `›` on the selected row, a status dot or fold arrow on a header) and the checkbox, so the columns after it move two cells over, and `ListLines::lead_width` (`views::common::lead_width`) is the one width the views and the mouse targets share. The lines among the rows (`done N`, `(no tickets)`, the shared line, Epics' progress line, the hidden Done line) indent by the same lead, so they line up while marking. `mouse::register_rows` makes the whole lead (the gutter, plus the checkbox's two cells while marking) the Mark target, and each item's fold cell is where `ListLines` put it: a parent's arrow column comes from its key cell (`views::common::KeyCell`), a header's glyph is `GLYPH_COLUMN`. Each list and pane registers the text a drag can select (`mouse::selectable`, `TextSelection::areas`), and a drag stays inside the area it started in. `ListLines::render` registers its list shifted by its own lead, so a copied row has no marker or checkbox and a drag that starts in the lead selects nothing. Filters' sidebar shifts by the gutter alone (it has no checkbox), and each pane's title is an area of its own, from its first letter. Muted cells use `views::common::muted`, which is gray on the selected row; its row is tinted across the full width (`tint`), with the key and summary bold.
- Lists have no header row, column bars or frame. A group header is `● Name count` (the dot in `style::status`, the name bold, the count muted) and one blank line follows each group; a folded done group reads `● Done 1  (z to open)`, and on My Work only a hidden one reads `● Done 1  (d to show)` under the groups (`App::hidden_done_count`, counted with the visible rows). A selected group header shows only the tint, not `›`, because its glyph slot holds the dot or fold arrow. Team, Epics and Unassigned headers keep `▼ name` plus counts, and status-grouped lists use `● Name count`. A sub-task is indented two cells and leads with `└ `; its parent keeps its fold arrow.
- Done tickets list the most recently updated first (`StatusRules::order_done`, which `StatusRules::group` and Team's done split both call); active groups keep their order, and sub-tasks still follow their parent because rows are nested after sorting.
- My Work, Team, Unassigned and Filters show an Updated column (before Labels where there is one): each ticket's age since Jira's `updated` in its largest whole unit ("59m", "23h", "6d", "3w"), from `views::common::age`. Each render reads the time once into `views::common::Ages`, whose `updated_cell` draws every age on screen, so they are all measured to the same moment.
- The detail pane's body (fields, description via `widgets/markup.rs`, comments oldest first) is pre-wrapped to the pane's width, so its line count is its height: the renderer records the scroll limit in `App::detail_scroll_max` for the scroll keys. Its first line is `KEY  N of M` and a `[×]` (`Target::CloseDetail`); the last column is the scrollbar, which draws only.
- Overlays (`widgets/`): a ticket or epic detail is two panes (`ticket_detail::panes`). From `SPLIT_MIN_WIDTH` (120) columns of content, unless `z` zoomed it, the list takes `LIST_WIDTH` (50) cells, one dim `│` divider the next, and the detail the rest; narrower, the detail takes the whole area and the list isn't drawn. `ui` passes the list's width to `views::render_active` as `compact`: `ListLines::ticket_row` then sizes the summary to what the key leaves and skips the other cells (Epics' progress line is skipped, Filters draws only its results). While the detail is open the status area (`status::status`) holds the detail's hints (`ticket_detail::hints`), wrapped by `footer::wrap_pairs` onto as many rows as the width needs and drawn by `footer::render_pairs`, which registers each key as a click target, so no key loses its target when the terminal narrows. A flash or a pending move takes a row of its own above them. The detail and an open panel are checked before the search and the pending move, so the hints stay while a search is still set. The detail's `begin_layer` clears the top bar's targets but the list's rows stay: `Target::Row` while a detail is open shows that row's ticket (`open_selected_row`) instead of the select-then-open rule. Every form, picker and notice is one `widgets::dock::Panel`: `dock::open` names the first open one, which is the one `handle_key` gives the keys (a test opens every pair), `dock::plan` sizes it from the rows its `rows` declare (`form::Row`, `form::need`, `form::split`) plus the rule, title and last row, up to 60% of the content but never under the rows' minimums, and the list above shrinks, keeping its selection in view (`ListLines::render` scrolls to the selected item). The panel's frame is `form::render_panel_frame` (one muted rule, a bold title line with a muted detail, `[×]` as `Target::Key(Esc)`), its fields are unboxed (`form::render_editor` and `render_choices`), its last row is buttons and hints (`form::button_row`) and the status line is blank while it is open. The move failure panel counts the rows Jira's error wraps to itself (`move_failure::wrapped_rows`, a port of ratatui's word wrap that a test compares with what a `Paragraph` draws) and scrolls with `j/k` when it is taller than the panel. The move picker and the bulk menus are `form::Menu`s drawn by `form::render_menu`. Help and Settings are sheets (`form::render_sheet`): they clear the whole frame and draw a title line, the body and a hint line. Settings gives Starting tab and Theme six rows each (a label and five options), so every tab and preset shows at 80x24 (custom themes beyond five still scroll the list). Help's hint line is `Esc/? close` after the scroll hint, and only that close hint is a click target, as a footer hint is its own. The first-run setup (`setup::render_setup`, before any theme exists) is a sheet too: `form::title`, labelled fields with a `style::cursor` and `style::button`s on the last row, with `setup::press` applying the keys.
- `delight.rs` holds the fun parts, all off with `preferences.delight = false` (`Delight::enabled`). `App::record_move` hands every move Jira confirms to `App::celebrate_move` (in `delight.rs`) with the ticket as it was: a move from an active status to a done one (not a dropped one) starts confetti, screen-wide when it finishes an epic, whose Epics progress bar's done cells then turn rainbow (`Delight::rainbow_bar`, which takes the bar's spans and leaves other runs their colors) and whose message `record_move` returns for the single move's or bulk move's status line. A running epic celebration isn't cut short by a smaller one. Moves, comments and created tickets are tallied for the receipt `main` prints after restoring the terminal. Confetti is drawn by `ui` over every overlay, before `Theme::apply`, and the event loop wakes every 33 ms while it falls (see "The event loop sleeps until woken"). Staleness (dusty from 21 days, fossil from 90) counts only active tickets; renderers get it through `views::common::Ages`, which reads the time once per render, so every age and a fossil's faded row (`Ages::fade`, applied to the row's base style) use the same moment. A stale ticket has no icon: it shows its age in the muted Updated column, and the detail view's `stale_quip` words the wait. The day comes from `date` once at startup (`delight::Today`), and the inbox-zero scene is picked then too. Spooky season (October 15th to 31st) changes the scene and the receipt's sign-off, adds a `S settings` hint to the footer until `theme::SPOOKY` is chosen (`Delight::suggests_spooky_theme`), and `views::common::status_label` shows Blocked as Cursed in status cells and group headers (the detail view keeps Jira's name).
