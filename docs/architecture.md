# lazyjira architecture

The rules behind lazyjira's reads, caches, statuses, moves and rows: what the code must keep true, and why. User-visible behaviour and keybindings are in [README.md](../README.md); the decisions with their alternatives are in [docs/adr/](adr/).

## Key Design Decisions

### Epics come from batched searches
The Epics tab's `jira_reads::fetch_epics` reads through `jira_rest::search` too, not one `jira` process per epic: one search lists the epics (`epics_jql`), then `epic_children_jqls` builds one children search per `jql::KEYS_PER_SEARCH` (50) epic keys, and `load_subtasks` one sub-task search per 50 children (`subtasks_jqls`). A project with 400 epics and 2000 children needs about 50 searches, so `jira_search::search_each` runs `SEARCHES_AT_ONCE` (4) at a time (`bounded::for_each_bounded`, which bulk actions use too) and `jira_search::search_in_order` returns their tickets in query order, stopping the queued ones from being sent once one fails. The limit is per read: an epics refresh and a detail prefetch can have up to 8 searches out at once.

A child names its epic through the Epic Link field (company-managed projects) or `parent` (team-managed). The `"Epic Link"` clause is left out when jira-cli's config has no `epic.link`, since the field would then be unreadable and the JQL could fail, so only `parent` links are found there. `lists::group_by_epic` puts each child under the epic its `epic_key` names (the Epic Link value, else a non-sub-task's `parent`), once each and sorted by key; a child of an epic that isn't listed is dropped. `subtasks::add_to_epics` adds the sub-tasks of the children, which Jira doesn't link to the epic, so progress counts them. Any failed search, sub-tasks included, fails the refresh (`refresh_epics_cache` returns the error), so the epics already on screen and in the cache stay instead of being replaced by epics with a different progress.

### Lists come from one Jira search
My Work, Team and Unassigned come from one paginated `jira_rest::search` ([ADR 0005](adr/0005-read-lists-over-jira-rest-search.md)), not per-member CLI queries. `jql::lists_jql` builds it from the config: the roster's active tickets (plus those done inside the window for the full scope) and the active tickets nobody has taken that are the team's by Assigned Teams. A REST search needs the project and an order spelled out, so every builder adds them (`scoped_jql` for saved filters, keeping their own ORDER BY), and every config string in a query goes through `jql::quote`.

Emails are normalized (`cache::normalize_email`) where they enter the app (Jira's issues, the roster, `jira me`), so everything after compares them exactly. `lists::bucket_tickets` splits the results: a ticket is placed on the roster by email, else by the assignee's display name, since Jira can hide emails; an assignee it can't place joins Team under their email (or display name) rather than dropping the ticket; no assignee becomes the Unassigned member's; My Work is the tickets of the current user's email. The Epic Link field id is jira-cli's `epic.link` (`jira_rest::epic_link_field`), never a hard-coded `customfield_` id. A search answer without a `total` is an error, not a short list. A failed search (including a missing `JIRA_API_TOKEN`) propagates out of `fetch_with_scope`, so `replace_cache` isn't called and the last snapshot stays; with no snapshot, startup restores the terminal and exits with the error.

### Detail data uses JSON + local cache
Rich ticket detail (description, reporter, comments as activity) is cached locally, and is hydrated on startup for fast detail open. Hydration (`hydrate_ticket_from_details_cache`) fills only those detail-only fields and the stored `detail_loaded`: labels, assignee, epic and parent come from the list search and the cache must not bring back stale values.

The details cache file is read once at startup into `local_cache::DetailCache` (`App::details`); `fetch_active_only` and `fetch_all` hydrate from that in-memory copy before returning, so no caller can forget to, and a background task writes it back once details stop arriving for 750 ms. `DetailCache::close` (called when the app quits) writes the file itself rather than asking that task, so details recorded in the last moments aren't lost and a stalled task can't hold up quitting. It also drops the details of tickets no loaded list holds any more (`App::listed_keys`: My Work, Team, every epic's children and the filter results), so the file doesn't grow with every ticket ever seen; with nothing listed (the lists never loaded) it drops nothing, and a dropped ticket is simply refetched when opened.

Missing details are prefetched in the background by `jira_search::fetch_ticket_details`: one `jira_rest::search` (`key in (...)`, asking for the list fields plus `DETAIL_ONLY_FIELDS`) per `KEYS_PER_SEARCH` (50) tickets, `SEARCHES_AT_ONCE` (4) chunks at a time, and each ticket's result goes to the app in its own `TicketDetailFetched`, so `enrich_ticket` and the move guard see each as a single-ticket detail. A chunk that fails (or a ticket Jira leaves out) fails only those keys: they stay missing and are asked for again on the next refresh, and the other chunks are still read.

A cached detail is never refreshed on its own (it is only pruned at quit), so opening a ticket's detail always fetches Jira's copy too (`App::open_fresh_detail`, through `jira_rest::issue`, as does the refetch after a move): the cached detail shows at once and is replaced when the fetch lands. That read is `GET /issue/{key}`, not a search, because the search reads Jira's index, which can lag a move made a moment ago. Neither read asks for the changelog, so activity is comments.

### Local caches
The snapshot, epics, ticket details and the current user's email (from `jira me`, refreshed in the background at startup once one is remembered) live in `~/.cache/lazyjira/`, per project, readable by the user only (directory 0700, files 0600: they hold descriptions and comments). Each is written through a temp file renamed over the cache file (`write_cache_text`), so overlapping saves (quit and the details writer, two lazyjira instances) and a crash never leave a half-written one; a cache directory or file an earlier build made readable by others is tightened when written. The epics and details caches 0.9.0 left in the system temp dir are ignored, and `local_cache::remove_old_temp_dir_caches` deletes this project's two files once at startup.

A cache that fails to parse is ignored and refetched, which is how format changes are handled: tickets store their status as `status_name`, so caches from before real status names are refetched once.

Tests use `lazyjira-test-<user>` in the temp dir instead (`local_cache::cache_dir`), with the process id in every file name so parallel runs don't share files; each test removes its files, and the directories it makes, even when it fails.

### Statuses
`Ticket::status` is Jira's own status name ("Resolved", "On Deck"), or `cache::UNKNOWN_STATUS` when a read's answer has none (so it shows plainly instead of passing as To Do; `enrich_ticket` never copies it over a real status). Views group, label and compare by it. `cache::StatusRules`, built from the `[statuses]` config, decides everything else about a status: the one display order (`active` in config order, then unlisted statuses in first-seen order, then `done`) and whether it's done (`is_done`: `d` hides it, epic progress counts it, Team puts it in the done split and leaves it out of active counts). Get it from `app.status_rules()`; don't sort statuses or test for done anywhere else. Names match case-insensitively. A name the config doesn't list takes the place of a listed name that `Status::from_str` reads the same way (so "Resolved" follows "Done"); failing that, Closed-like names are done and anything else is active.

The `Status` enum is only Jira-independent knowledge: move shortcut keys, default colors (`views::common::status_color`), and that fallback. `Status::from_str` reads Done/Closed/Resolved as `Status::Closed` and unknown names as `Status::Other`.

The `[statuses]` config also controls which statuses the JQL queries load.

### Moves use Jira's transitions
Each issue type has its own workflow, and a transition's name can differ from the status it leads to, so moves always send a transition id, never a status name. The picker lists the ticket's transitions from `GET /rest/api/2/issue/{key}/transitions?expand=transitions.fields` and sends the chosen one by id (`jira_rest`). Shortcuts match a transition's destination through `Status::from_str`. Transitions that differ only by id are merged when parsed. A resolution is asked for only when the transition has a resolution field, from that field's allowed values.

### Moves wait for Jira
A single-ticket move changes the ticket only after Jira reports success (`BackgroundMessage::TicketMoved`); a failure keeps the status and shows the error until dismissed. Every Jira read (detail fetch, cache/epics refresh, filter query) carries `requested_at = app.moves.now()`. Reads requested before a ticket's latest confirmed move leave its status alone, so write statuses only through `App::enrich_ticket(key, requested_at, detail)`, `App::replace_cache(cache, requested_at)` or `App::reapply_moves_since`; never write them directly.

### Visible rows
App's grouped view methods return `VisibleGroup` values with header metadata, totals, and occurrence indices. Collapsed groups retain their header and totals but have no ticket rows. Navigation and renderers use these same groups; renderers compare supplied indices with `selected_index`. Keep tab-specific formatting in `views/`. Team members are ordered by active ticket count (most active first), with active tickets before done tickets.

Use `App::switch_tab` to restore each tab's position, search, and status focus. Cache updates preserve the selected ticket occurrence and group through `mark_cache_changed`; use `replace_cache`, `replace_epics`, and the ticket update helpers so the old visible rows are retained before data changes.

Renderers register mouse targets for the rows actually drawn, after scrolling. `ui` clears targets before each overlay, so covered controls cannot receive clicks. Mouse actions share keyboard handlers and preserve confirmation steps. Text fields use the existing `tui-textarea` dependency and `widgets::form` helpers.

### Sub-tasks nest under their parent
`Ticket::parent_key` names a sub-task's parent. It comes from Jira's REST search on every list read: from the list search itself for My Work, Team, Unassigned and filters (`fetch_with_scope`, `fetch_jql_query`) and for epics' children, and from the sub-task search (`jira_reads::load_subtasks`, through the same `search`; [ADR 0004](adr/0004-read-subtask-parents-over-rest.md)) for the sub-tasks `fetch_epics` adds. Only those reads and a freshly fetched detail (through `enrich_ticket`) set it: `hydrate_ticket_from_details_cache` skips it so a re-parented ticket doesn't keep its old parent. A failed search fails the read, so rows stay as they were.

Sub-tasks of an epic's children count in epic progress (see "Epics come from batched searches"). Each tab passes its rows through `subtasks::nest` when building `VisibleGroup`s; Team nests its active and done rows separately, so a sub-task never moves between them. Renderers get a row's key and summary from `views::common::ticket_cells`: a sub-task whose parent is in the same rows is indented, and one whose parent isn't (a different status group, another assignee) leads its summary with the parent's key. `jira_issue::ticket_from_issue` reads a sub-task's `parent` as `parent_key`, never as an epic.

Folding a parent adds its key to `App::collapsed_parents` (one set for every tab). `nest` tags each row with its `Family` (a parent with a sub-task count, or a child); `index_groups` drops the children of folded parents from the rows but keeps them in `total` and `VisibleGroup::folded_subtasks`, and `VisibleGroup::family` carries the tags to renderers and to `selected_fold_parent`. So row counts that must include hidden rows (Team's header counts) come from `total`, never from `tickets.len()`, and Team splits active from done by status, not position. `z` goes through `App::toggle_fold_at_cursor`: the selected parent or sub-task folds its parent, anything else folds its group.

### Themes recolor the finished frame
Renderers draw with plain ANSI colors, each used for one job: `DarkGray` is muted text as a foreground and the selected row as a background, `Cyan` is keys and focus, `Yellow` is headers and the chosen option, and so on (`Theme::role` lists them). `ui` ends with `Theme::apply`, which swaps those colors in the buffer for the theme's roles, like a terminal color scheme. So keep drawing with the ANSI color for the job, not a theme field, and code that finds things by color (the footer's key hints, the editor cursor) keeps working. Unset roles, and every role of `default`, leave the terminal's color. While preferences are open, `ui` applies the highlighted theme instead of `App::theme`, which is how the picker previews.

## Current UX behavior
- Team view includes the current user (if not in the `[team]` config, inferred from `jira me` email).
- My Work and Team include Epic and Labels columns. An epic or labels every drawn row shares show once, muted, on a line under the column headers instead (`views::common::Shared`, used by My Work, Team, Unassigned and Filters, each passing the `Columns` it has: only My Work and Team have Epic and Labels columns, and Unassigned, grouped by epic, leaves the epic off the line; Team draws it only under its first member's headers): rows with no epic don't count, the Epic column returns when two rows' epics differ, Labels keeps only the labels some rows lack, and a hidden column's width goes to the summary. The sub-tasks of folded parents count; rows of folded groups don't.
- `Enter` works while search is active (opens detail for selected row).
- Done status groups start folded. In My Work, `replace_cache` folds each done status the first time a read brings it, until the first full-scope read (Full or Manual) is applied through `App::replace_cache_full_scope`, which folds its own new done statuses and then ends folding, since the snapshot and the active-only read may lack done tickets. A failed read changes nothing. After that no read folds, so an unfolded group stays open and a group that first appears mid-session (a ticket just closed) shows open. In Filters on every query (`App::show_filter_results`).
- Selection marks are ☐ (unselected, muted), ☒ (selected) and ⊟ (some of a group), one column each, from `views::common` (`ticket_marker`, `group_marker`). Each tab calls `color_marks` after `highlight_row` to color a line's first mark, and `mouse::register_rows` finds the mark the same way, by display width (`unicode-width`), and makes the cell either side of it clickable too. Muted cells use `views::common::muted`, which is gray on the selected row.
- Done tickets list the most recently updated first (`StatusRules::order_done`, which `StatusRules::group` and Team's done split both call); active groups keep their order, and sub-tasks still follow their parent because rows are nested after sorting.
- My Work, Team, Unassigned and Filters show an Updated column (before Labels where there is one): each ticket's age since Jira's `updated` in its largest whole unit ("59m", "23h", "6d", "3w"), from `views::common::age`. Each render reads the time once and passes it to `updated_cell`, so every age on screen is measured to the same moment.
- The detail overlay's body (fields, description via `widgets/markup.rs`, comments oldest first) is pre-wrapped to the overlay's width, so its line count is its height: the renderer records the scroll limit in `App::detail_scroll_max` for the scroll keys.
